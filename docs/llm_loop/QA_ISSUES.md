# QA 문제 및 해결 기록

이 문서는 문제를 발견한 순서대로 누적한다. 문제를 삭제하지 않고
`OPEN → REPRODUCED → FIXED → VERIFIED` 상태로 이동한다. `VERIFIED`는 원인 증거,
재현 테스트, 유사 사례·반례, 전체 회귀가 모두 통과했을 때만 사용한다.

## 작성 형식

| 항목 | 내용 |
|---|---|
| ID | `QA-0001` 형식 |
| 상태 | `OPEN`, `REPRODUCED`, `FIXED`, `VERIFIED`, `BLOCKED`, `WONT_FIX` |
| 심각도 | `P0`, `P1`, `P2` |
| 분류 | QA 계획의 문제 분류 코드 |
| 증상 | 사용자가 보거나 평가에서 확인된 현상 |
| 증거 | 질문 ID, 원문, 결과 파일, 로그 |
| 원인 | 재현으로 확인한 직접 원인 |
| 해결 | 실제 변경 내용 |
| 검증 | 추가한 테스트와 재실행 결과 |
| 영향 범위 | 영향을 받는 계층·질문 유형·API 경로 |
| 산출물 해시 | 재현 입력·결과·런타임의 SHA-256 |

## 현재 열린 문제

### QA-0001 — 답변 가능한 질문을 확인 불가로 거절

- 상태: `FIXED`
- 심각도: `P0`
- 분류: `VERIFICATION`
- 증상: 답변 가능한 신규 블라인드 5건을 `제공된 회의록에서 확인할 수 없습니다`로 거절
- 증거: `blind-040`, `blind-047`, `blind-069`, `blind-077`, `blind-084`
- 원인: 5건 모두 gold source가 검색 Top 5에 있었다. 검증기가 `하면서·않느냐며·따라·요구는·보이도록·되도록·정도인지·간사와·말고`를 사람 이름으로 오인했다. `blind-077` 1차 답변의 `안규백`은 실제 미지원 인물이었지만 재생성 답변의 `정도인지`를 다시 인물로 오인해 최종 거절했다.
- 해결: 근거에 없는 이름 후보에만 한국 성씨 구조를 요구하고, 활용형·연결어를 비인명으로 판별하도록 보강했다. 실제 근거 화자는 성씨 목록과 무관하게 보존한다.
- 검증: 실제 오탐 5계열과 실제 미지원 인물 반례 테스트 PASS, 검증기 30 PASS, 전체 258 PASS.
- 남은 확인: 신규 E2E에서 동일 5개 문형의 오차단 0을 확인해야 `VERIFIED`로 승격한다.

### QA-0002 — 인용 전문에 없는 핵심 주장 생성

- 상태: `REPRODUCED`
- 심각도: `P0`
- 분류: `RETRIEVAL / SCORER / GENERATION / VERIFICATION`
- 증상: 독립 의미채점이 인용으로 지지되지 않는 주장 또는 금지 수치를 검출
- 증거: `blind-021`, `blind-024`, `blind-048`
- 원인: `blind-021`은 gold chunk 바로 앞 chunk만 최종 근거로 남았는데 채점기가 같은 source ID라는 이유로 인용 성공 처리했다. `blind-024`는 원문의 `공단`을 `국가철도공단`으로 임의 확장했다. `blind-048`은 다른 인용에는 존재하지만 질문이 요구하지 않은 `0.06·0.07` 수치를 추가했다.
- 해결: 문서 ID가 아니라 정확한 gold chunk 인용을 요구하도록 결정 채점과 최종 게이트를 수정했다. 근거·질문에 없는 구체 기관명 확장을 치명 오류로 차단했다. 생성 프롬프트에 질문 항목과 직접 대응하지 않는 배경·수치 삭제 및 축약 기관명 확장 금지를 추가했다.
- 검증: 같은 문서의 다른 chunk 반례, 기관명 확장 정탐·오탐 방지, 품질게이트 연결 테스트 PASS. 진단 재채점에서 `blind-021`이 `gold_evidence_not_cited`로 검출됨. 관련 100 PASS, 전체 258 PASS.
- 남은 확인: `blind-021`의 검색/RRF 단계에서 gold chunk가 최종 Top 5에서 탈락한 원인은 RRF 변경 보류로 미해결이다. `blind-048` 범위 준수도 신규 E2E 확인이 필요하다.

### QA-0003 — 한글 수사와 숫자 표기 동치 오탐

- 상태: `VERIFIED`
- 심각도: `P1`
- 분류: `SCORER`
- 증상: 실제 답변의 `3대`와 골드의 `세 대`를 다른 값으로 판정
- 증거: `blind-049`, 독립 의미채점 `PASS`
- 원인: 숫자 정규화가 한글 수사와 아라비아 숫자를 같은 값으로 변환하지 않음
- 해결: 고유어 수사+단위(`세 대`, `세 명`)만 숫자 표현으로 정규화하고, 일반 단어 속 음절(`세부`, `세계`)은 숫자로 인정하지 않도록 수정했다.
- 검증: `세 대↔3대`, `세 명↔3명` 동치와 `세부·세계` 반례 테스트 PASS, 채점기 10 PASS, 전체 258 PASS.

### QA-0004 — 질문 범위 밖 exact value 자동 실패

- 상태: `VERIFIED`
- 심각도: `P1`
- 분류: `DATA / SCORER`
- 증상: 질문이 조문 번호 자체를 요구하지 않는데 `93조` 누락을 자동 실패로 처리
- 증거: `blind-022`, 독립 의미채점 `PASS`
- 원인: 골드의 참고 exact value와 질문이 반드시 요구한 exact value가 구분되지 않음
- 해결: 신규 골드 생성부터 `required_exact_values`와 `reference_values`를 분리하고, 자동 누락 실패는 전자만 검사한다. 두 목록의 중복 및 합집합 불일치를 스키마 검증에서 차단한다. 구형 동결 데이터는 재현성을 위해 기존 `exact_values` 규칙을 유지한다.
- 검증: 필수 숫자 누락 실패, 참고 숫자 누락 비실패, 분할 중복·합집합 오류, 생성→검증→의미채점 입력 전달 테스트 PASS. 관련 35 PASS, 전체 258 PASS.

### QA-0008 — 검색 단계별 trace 부족

- 상태: `FIXED`
- 심각도: `P1`
- 분류: `OBSERVABILITY / RETRIEVAL`
- 증상: 저장된 최종 결과에는 최종 Top 5만 있어 keyword·vector 후보, RRF 순위, LLM rerank 전후 중 어느 단계에서 gold chunk가 탈락했는지 한 파일로 증명할 수 없다.
- 증거: `blind-021`은 최종 인용이 `_chunk_001`, gold는 `_chunk_002`이지만 pre-RRF/RRF/post-rerank 후보 기록이 없음.
- 원인: 검색 hit의 `kw_rank·vec_rank·rrf·rerank_rank`가 답변용 source 요약 과정에서 제거되고, candidate pool은 런 결과에 저장되지 않음.
- 해결: 기존 list 검색 결과 계약을 유지하는 `SearchResults`에 keyword·vector·RRF·최종 문맥 순위를 부착했다. 평가 요청만 `include_trace=true`로 trace를 받고 일반 UI 응답에는 노출하지 않는다. 감사기가 trace 누락을 실패 처리하며, 별도 분석기가 RRF Recall@10·최종 문맥 Recall@5·유형별 Recall·필터 오류를 계산한다. RRF 계산식·가중치·정렬은 변경하지 않았다.
- 검증: 단계별 순위와 최종 결과 순서 불변, API opt-in/일반 미노출, trace 누락 감사 실패, 단계별 recall·필터 오류 반례 테스트 PASS. 전체 263 PASS.
- 남은 확인: 신규 E2E 결과에서 실제 trace 100/100 저장을 확인한 뒤 `VERIFIED`로 승격한다.

### QA-0009 — 코드의 portfolio 합격선이 고정 목표보다 낮음

- 상태: `VERIFIED`
- 심각도: `P0`
- 분류: `SCORER`
- 증상: 코드가 전체 85%·인용 90%·거절 90%를 portfolio PASS로 허용해 문서의 90%·95%·100% 목표와 충돌.
- 증거: `summarize_gate.py`, `summarize_hard_veto.py`의 이전 `portfolio` 프로필.
- 원인: 2차 실패 후 완화한 임시 기준이 고정 목표 결정 이후에도 코드에 남음.
- 해결: portfolio 기준을 전체 90%·인용 95%·거절 100%·치명 오류 0으로 상향하고 하드게이트 허용 자동 실패를 10건으로 제한했다.
- 검증: 기준 고정 테스트와 최종 게이트 테스트 9 PASS, 전체 258 PASS.

### QA-0010 — 자동검사만으로 130개 골드를 일괄 승인 가능

- 상태: `FIXED`
- 심각도: `P0`
- 분류: `DATA / SCORER`
- 증상: `approve_codex_source_review.py`가 구조 검증 PASS만 확인하고 모든 문항을 동일 reviewer·note로 자동 승인할 수 있어, 문항별 의미 검토를 했다는 증거가 없었다.
- 증거: 이전 스크립트는 별도 검토 파일 입력 없이 120개 답변 가능 문항과 10개 부정문항을 모두 `approved`로 생성했다.
- 원인: 자동 구조 검사와 독립 의미 검토를 하나의 승인 단계로 간주했다.
- 해결: 별도 `gold_reviews_completed.jsonl`을 필수 입력으로 요구한다. 130개 ID 일치, 문항별 approved 상태, 검토자, ISO 시각, 구체 메모, 질문 범위·원문 지지·주장 범위·필수값·참고값 5개 체크를 모두 검증해야 최종 승인표를 만든다. 검토 문서도 필수값과 참고값을 분리해 표시한다.
- 검증: 명시적 문항별 검토 통과, pending·누락 거부, 구형 단일 exact 체크 거부 테스트 PASS. 승인·렌더링 관련 18 PASS.
- 남은 확인: 신규 130문항 검토에서 실제 completed 파일과 승인 해시를 생성한 뒤 `VERIFIED`로 승격한다.

### QA-0011 — 평가 API만 gold 날짜·위원회 필터를 직접 주입

- 상태: `VERIFIED`
- 심각도: `P0`
- 분류: `INFRA / FILTER`
- 증상: 프론트는 `/query`에 `question+mode`만 보내는데 평가 실행기는 gold의 committee·date_from·date_to를 추가해 더 유리한 검색 조건으로 시험했다.
- 증거: `frontend/src/api.js::postQuery`와 이전 `run_baseline.py::request_query` 요청 body 불일치. 이전 82점 결과도 이 필터 주입 조건에서 측정됨.
- 원인: 같은 `/query` URL을 사용하면 경로가 동일하다고 보았고 요청 payload 동등성을 검사하지 않았다.
- 해결: 평가도 프론트와 동일하게 `question+mode`만 의미 입력으로 보낸다. `include_trace`는 관측 전용이다. 날짜·위원회는 질문 파서가 추출하며, 실제 추출 필터가 gold와 다르면 G2 trace 분석에서 실패한다.
- 검증: UI 함수와 평가 요청의 route·semantic field 동등성, gold 필터 미주입, 실행 감사 계약 테스트 12 PASS.
- 영향: 과거 82점은 현재 제품 대표 점수로 재사용하지 않는다.

### QA-0013 — 회의 날짜와 질문 본문 날짜를 하나의 검색 범위로 합침

- 상태: `VERIFIED`

- 원인: 일부 동결 gold의 `required_exact_values`에 답변 요구값이 아닌 질문 범위 메타데이터가 포함됐다.
- 처리: 블라인드 공개 후이므로 공식 81점은 사후 수정하지 않는다. 다음 데이터 동결기는 날짜·위원회·질문 속 인물을 기본 `reference_values`로 보내고, 질문이 명시적으로 요구할 때만 required로 허용해야 한다.

### QA-0043 — 최종 치명 오류 4건의 사후 일반 보완

- 상태: `FIXED / LOCAL_VERIFIED`
- 심각도: `P0`
- 분류: `VERIFICATION / GENERATION / CONTEXT`
- 대상: `blind-005·010·016·059`.
- 해결: 명시 수치의 직접 차이 산술 검증, 상대 시점 인물 오탐 제거, 조 단위 뒤 억 원 생략 동치, 전후 종점값 보존 가드, 비정당 질문의 당적 비노출·후처리를 구현했다.
- 검증: 대상 답변·검증 62 PASS, 전체 336 PASS, 실패 0.
- 한계: 최종 블라인드는 이미 공개됐고 사용자가 추가 검사를 종료했으므로 API 재평가를 하지 않았다. 공식 점수는 81점과 치명 오류 4건을 그대로 유지하며, 수정 후 성능 향상을 주장하지 않는다.
